# GAMESOL Navigation Polish

## Scope And Verdict

First focused polish pass, not a claim that every game screen has been redesigned. Keep the playable devnet game and existing transaction behavior. Improve the game shell before adding NFT mechanics.

Existing-player loop: choose an owned world, issue one construction or fleet command, then return to its system to inspect the wider universe.

## Cold-Start Observations

The live `/app` opened the public universe, showed navigation and governance controls, and offered Start Playing on desktop. Moving inward showed a large arrival title over a temporarily empty 3D view. On a narrow viewport, Start Playing disappeared and the coordinate-jump control could extend beyond the screen.

Highest-impact problems, in priority order:

1. Mobile sign-in was hidden by the legacy rule suppressing direct children of the account header. Restore it with a reachable touch target.
2. Cross-level navigation recreated the WebGL canvas. Preserve the renderer and change its contents under a short transition.
3. Planet entry/exit used a timed, fabricated planet graphic unrelated to destination readiness. Replace it with cover -> load -> rendered-frame readiness -> reveal. Do not reveal an unfinished scene on a timer.
4. Controls mixed tiny text, arbitrary box sizes, typographic symbols, and unclear LEVEL IN/OUT commands. Use the existing button primitives, Lucide icons, context-specific destinations, visible focus, and 44px primary targets.
5. Mobile coordinate, governance, and account controls collided. Give them explicit, bounded positions and a separate layout below 360px.

## Implemented

- One WebGL canvas across universe/galaxy/system navigation; lower maximum map DPR from 1.75 to 1.5.
- Shared scene-transition lifecycle for map and planet/system navigation. Wait for two scene frames after the relevant suspense boundary resolves; show a recoverable error if loading exceeds 15 seconds.
- No fabricated globe or long, full-screen arrival announcement.
- Short, smooth camera focus/zoom movement. Direct camera input cancels scripted movement; an old zoom command is not replayed when view bounds change.
- Reduced-motion preferences eliminate movement durations but retain readiness checks.
- Larger, consistent navigation, account-entry, world-back, command-dock, and facility-inspection controls. Existing Lucide and game-button primitives are reused.
- Game account, planet and NFT economy/program behavior remain unchanged.

## Verification

- Hosted TypeScript and production builds pass.
- Six focused UI/motion tests and thirteen NFT regression tests pass.
- Public universe -> galaxy -> system -> galaxy navigation exercised in the hosted build.
- Desktop screenshots sampled for nonblank scene pixels: universe 413/1782, galaxy 553/1782, system 653/1782 pixels above the chosen brightness threshold. The sample excludes the main left HUD.
- Desktop/mobile layout inspected through browser screenshots and DOM bounds; mobile defects found during this check were repaired before official alias promotion.

- No SBF/WSL builds or multiple local dev servers were launched.

## Next UX Slice

For a 30-second returning-player turn: open the current world, select an available build or fleet action, review its cost and queue state, issue it, and return to the system. Keep one primary action visible at each step.

- Keep: actual 3D worlds, live resource costs, queues, fleet actions, wallet ownership, existing NFT portraits, and real on-chain confirmations.
- Delay/reveal contextually: governance details, market explanations, account infrastructure, and dense progression tables.
- Remove: artificial travel illustrations, competing arrival titles, and text-only substitutes for familiar tool icons.

The next coherent pass should standardize the remaining fleet/store/workspace buttons and their pending/error/success states, then validate the signed-in planet loop on desktop and phone. Do not add explanations to compensate for a confusing control layout.

## Fleet And Store Follow-Up

Implemented the next focused slice:

- Shared 44px action buttons with a stable icon slot, pending labels, native disabled state, and accessible busy state. Only the selected production/mission/purchase action shows progress; sibling actions are disabled.
- Fleet/defense quantity presets, labelled icon steppers, and whole-number validation bounded by the transaction client's u32 format. Invalid input blocks production rather than silently rounding it.
- Whole-number mission coordinates, fleet assignments, speed and cargo checks. Mission fields are disabled while target checks/launch are pending. A failed target check now remains visible instead of being hidden by the generic successful-preflight message.
- A quieter store with the original USDC token artwork, nonzero resource contents, explicit insufficient-balance state, purchased/reset state, and a review/cancel step before purchase submission.
- Purchase review shows the exact price, destination world, game-account USDC balance, contents and reset/cap conditions. Keyboard focus is trapped and restored; Escape does not dismiss the underlying workspace.
- Store read errors offer retry. Late reads from an old client/workspace are ignored; purchase review closes when the game client or destination changes.
- Existing prices and rewards were moved unchanged into a shared catalog. All catalog prices are checked against the existing transaction client. Global transaction success/error handling remains authoritative; no new success message is inferred from a resolved UI promise.

Validation: eight new command-control tests, six scene/motion tests, and thirteen NFT tests pass. A local, wallet-free component harness exercised decimal rejection, presets, pending/purchased states, review/cancel, keyboard focus, and desktop/390px/320px layouts. A long destination name wrapped without horizontal overflow. The harness uses explicitly labelled simulated balances/state, canonical pack metadata, and no RPC/wallet/transaction code. It is excluded from Vercel deployment by the existing `test` ignore rule, and the single memory-limited local server was stopped after verification.

Remaining acceptance boundary: real-account production, fleet launch, store retry against a live provider failure, and a real devnet purchase still require signed-in gameplay verification. No funds were spent, no fleet order was sent, and no NFT utility or reward changes were enabled.

## Construction And Research Follow-Up

Construction upgrades, research orders and laboratory upgrades now use the shared pending-action controls and command lock. Existing resource, prerequisite and queue gates remain unchanged. Active queues expose accessible progress values, distinguish free completion from "Finish with AM", and prevent duplicate submissions while another command is pending. Queue controls have larger mobile targets and normal text spacing.

Validation: all nine command tests pass, including the new construction/research/queue guard regression; frontend type checking passes. Desktop (1280px), narrow mobile (320px) and mobile (390px) component layouts were checked without a wallet. Pending research disabled the test controls; active/ready queue states retained their correct disabled actions. This is component-layout proof, not signed-in gameplay or transaction proof. The wallet-free harness remains excluded from deployment, and its local server was stopped before the cloud build.
